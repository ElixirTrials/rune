# Adversarial review of `remediation_plan_v1.md`

**To:** AI Researcher (record) · **From:** Adversary · **Scope:** the plan itself, not the paper.
**Reference material:** `HANDOFF_v13_review.md`, `v13_review_findings.json` (28 findings). Verified facts (from the researcher's handoff) used below without re-derivation: MBPP splits 374/500/90/10; Rune trained on 224 tasks; ~750/~203 raw-disjoint headroom exists but the +0.105 metric requires *gold trajectories*, not raw problems; episodic-vs-floor McNemar p=2.98e-6; scale0→c3 McNemar p=0.69; objective sign test binom(17,24)=0.064; n=10 held-out Fisher p=0.30.

---

## Verdict

**sound_with_revisions.** The plan is honest, well-scoped, addresses at prose or run level essentially every one of the 28 findings, and — commendably — pre-registers gates that name the outcome that would force a reframe rather than only the outcome that would confirm the win. It is not a rubber-stamp job. But three items keep it from `sound_proceed`:

1. The **`a2_tail` fallback reframe** ("weight-space delivery removes the need to know *in advance* which symbol to place near the cursor") is not itself tested by the proposed experiment. If the primary gate fails, that reframe becomes a post-hoc rescue whose central premise — that the adapter's conditioning is *not* oracle-supplied — is nowhere audited in the plan.
2. **M4 Option B** ("engage ReasonCACHE in Related Work") is a placeholder, not an argument. It closes the framing overclaim (`we test that boundary directly`) but leaves the *substantive* challenge — ReasonCACHE's theorem that KV/prefix expressivity strictly dominates low-rank weight updates — uncontested next to a cite the paper deploys as support.
3. **Phase 2a's feasibility question is punted to the Adversary**, but the actual dependency is a corpus check the author can do without the Adversary's input: does the corpus contain gold trajectories on any disjoint pool of adequate size? Everything downstream (run vs. prose downgrade) is decided by that lookup.

**Single biggest risk:** if the a2_tail run comes back at parity (a genuinely possible outcome given the adapter's conditioning surface fits six times over in the budget), the plan's reframe becomes the load-bearing story — and the reframe requires an experiment the plan does not commit to.

---

## Critiques

1. **[serious] Phase 1a `a2_tail` fallback reframe — untested rescue.** The plan's contingency ("the win is not 'weight-space beats prompt delivery under a budget' but 'the adapter internalizes retrieval; the prompt arm needs an oracle to know what to place'") presumes something the plan does not audit: that at inference time the hypernetwork's ~124-token conditioning is derived from the trajectory rather than injected by the eval harness. If it is trajectory-derived, then the adapter's conditioning is a non-trivial retrieval product and the reframe has content — but then the *fair* a2_tail arm should place the *same trajectory-derived string* in the prompt tail, not the gold symbol+definition. If it is oracle-injected (the eval hands the hypernetwork the gold symbol), then both arms are oracle-conditioned; a2_tail is a fair *channel* test but the retrieval reframe is unsupported in either direction. **Recommendation:** before running a2_tail, document explicitly (in one sentence in the plan, and one paragraph in Setup) what the hypernetwork receives at test time on the keystone: is it the gold cross-file symbol+definition, or a trajectory-derived summary that *contains* the symbol among trajectory tokens? If the former, list "adapter internalizes retrieval" as an unmeasured hypothesis, not a fallback. If the latter, define what string a2_tail actually places — the identical string the hypernetwork gets, or the raw trajectory slice from which it derives.

2. **[serious] Phase 1c Option B — "engage in Related Work" is not an engagement.** ReasonCACHE's abstract asserts a theorem — KV/prefix expressivity strictly dominates rank-r weight updates because low-rank ties expressivity to input rank — that directly targets the paper's core mechanism. Option B's prose fix removes only the *promise* to test that boundary; the theoretical challenge is untouched. Silently dropping "we test that boundary directly" without addressing why the theorem does or does not bite in the deployed regime reads to a KV/prefix-literate reviewer as retreat. **Recommendation:** if Option B is chosen, add one paragraph (Related Work or §5.4 discussion) that either (a) concedes the theorem's premise and argues the deployment regime is not expressivity-limited (e.g., the required rank on the keystone task is small; empirical LoRA rank at the operating point matches or exceeds the "input rank" a fair prefix would need), or (b) challenges an assumption of the theorem (e.g., ReasonCACHE assumes single-layer prefix injection; multi-layer LoRA composes in a way the theorem does not cover). Without one of these, Option B is a dodge — and the plan's own self-diagnosis ("the framing overclaim is the real defect and prose fixes it honestly") is only half true: prose fixes the framing defect, not the substantive gap the framing was papering over.

3. **[serious] Phase 0 venue effort estimate under-scopes the NeurIPS branch.** The plan quotes "decision + 1h build" for B2. TMLR at 15 pp with a class swap and anonymization is roughly that. **NeurIPS 2026 is not.** 15 pp → 9 pp of main text is a ~40% content compression that requires moving §4.2 grid detail, at least part of §5, and appendix-facing prose out of the main body while preserving load-bearing definitions used later — genuinely a day or more of restructuring, not an hour, and the restructure will collide with the Phase 3 prose fixes on the same paragraphs (P4/P5/M2/M3 all live in §1, §5.4, and the abstract). **Recommendation:** either commit to TMLR up front and drop the NeurIPS build entirely (the plan's stated default), or budget the NeurIPS branch as a 1–2 day restructure that must precede — not follow — Phase 3 prose, because a 9pp cut will silently displace prose you were about to rewrite.

4. **[serious] Phase 1a "no eviction" is imprecise about the budget accounting.** The plan says "no eviction (124 ≪ 768)". 124 fits, but the other 644 tokens of the 768-token window must be occupied by *something*, and in the floor arm those 768 tokens are (as I read it) cursor-adjacent code. Adding a 124-tok tail pointer therefore *displaces* 124 tokens of near-cursor context relative to floor. The comparison is still fair, but it is not "free" — a2_tail buys the pointer at the cost of 124 tokens of local code, and the honest way to report this is as a within-budget trade, not as an addition. This matters because if a2_tail comes in *below* floor's cursor-code baseline in some strata, the plan needs to attribute that to the trade, not treat it as evidence that the pointer failed. **Recommendation:** state explicitly what a2_tail displaces (which tokens of the floor's 768 are evicted to make room for the 124-tok tail pointer), and either (a) report a2_tail and floor with matched cursor-code lengths so the pointer's marginal contribution is clean, or (b) include a "tail padding" control (124 tokens of neutral filler in place of the pointer) to isolate the "pointer" contribution from the "different tokens" contribution.

5. **[moderate] Phase 1b swap control has no quantitative gate.** "Recovery must fall to floor (0.150)" and "if elevated → partly a frequency artifact." Elevated *how much*? A drop from 0.517 to 0.30 is neither "at floor" nor "still elevated" — it is exactly the ambiguous middle where the memorization-vs-retrieval attribution is contested. **Recommendation:** pre-register a numeric threshold with a CI, e.g., "swap-condition recovery within Wilson CI of floor → cleanly refutes; swap-condition recovery strictly above floor CI but below CI of episodic → partial confound, quantify as (episodic − swap) / (episodic − floor) = fraction attributable to conditioning content; overlapping episodic CI → frequency artifact dominant." State this before running.

6. **[moderate] Phase 2a feasibility is a corpus lookup, not an Adversary question.** The plan asks the Adversary to check whether "the corpus [can] supply a genuinely disjoint fresh pool of adequate size." I cannot — I have the split numbers (374/500/90/10 full-MBPP, 427 sanitized, 224 used) but not the corpus schema for which of those tasks have *gold trajectories* attached, which is the actual gating requirement. **Recommendation:** treat this as a Phase 0 action for the author (query the corpus manifest for tasks with gold trajectories, cross-reference against the ones used in objective-grid selection and the N=60 keystone set, report the disjoint count). If ≥ ~50 with trajectories exist, 2a is feasible; if not, the plan should say concretely what the prose downgrade looks like *now*, not leave that path unwritten.

7. **[moderate] Q4 encoder narrowing is scoped only to §3.2.** Narrowing to "Perceiver beats mean-pool" in §3.2 is correct, but the paper very likely echoes the stronger "architecture is not what gates this" framing elsewhere (intro contributions, §5 discussion, §6 limitations). The plan does not commit to a paper-wide `grep -n "architecture"`-style pass to catch downstream restatements. **Recommendation:** add a Phase 3 sub-item: audit every occurrence of "architecture", "encoder", "gating", "insensitive" and narrow each to match the §3.2 evidence.

8. **[moderate] "Option A next round" is a soft commitment.** Deferring the ReasonCACHE / KV run to next round is defensible for THIS submission — provided there is a durable commitment mechanism. The plan does not name one (pre-registration file, footnote in §6.3, explicit table entry). Without it, "next round" becomes "not run", and the same finding re-appears at the next review. **Recommendation:** add a named unrun-comparator table in §6.3 with the row `ReasonCACHE / prefix-tuning, W=768, N=60 keystone set — committed for next revision` and check it against the pre-registration list.

9. **[moderate] The plan does not address P9's substantive figure suggestion.** P9 has two parts: (a) delete stale `figure2.pdf` (which the plan handles) and (b) *consider a recovery-vs-budget-W curve* to make the "advantage grows as the budget tightens" claim visual rather than tabular. The second is a real proposal — it directly targets the strongest form of the keystone claim and would use existing data at additional W values if available. The plan is silent. **Recommendation:** either accept and add a Phase 3 figure sub-item (cheap if the harness already logged W-swept results; skip if only W=768 was ever run), or explicitly decline with a one-line reason.

10. **[minor] Fig. 2 print-size legibility QA is not addressed.** P9 also asks the author to eyeball compiled Fig. 2 at print size (axis labels, four-arm labels, Wilson whiskers, colour thread). Trivial to do, easy to forget; add a Phase 0 checklist item.

11. **[minor] Multiple-comparison correction across the new arms is not discussed.** Phase 1 adds two arms (a2_tail, swap) and, under Option A, a ReasonCACHE/prefix arm; Phase 2a adds one re-estimate — up to four pre-registered p-thresholds (three under Option B). Four preregistered gates at α=0.05 is a family-wise error rate near 0.19 (1−0.95⁴≈0.1855); three gates give ≈0.14. **Recommendation:** either state that each gate is independently pre-registered against a specified alternative (so per-comparison α is defensible) or apply Holm/Bonferroni. Not a fatal issue — the gates aren't fishing — but worth naming.

12. **[minor] Phase 0 says the venue decision is "author decision required," Phase 3 prose depends on venue.** This is fine as flagged, but the plan's own critical-path claim ("Phase 0 unblocks everything") is inconsistent with running Phase 1 in parallel — Phase 1a's exact abstract wording depends on TMLR vs. NeurIPS length constraints. Serialize or say so.

## Answers to the four open questions

**Q1 — Is `a2_tail` with an oracle-placed gold pointer a fair comparator?**
As a *channel* test, yes — both arms carry the identical ~124-token content, and the delivery mechanism (weights vs. tail-of-prompt) is the axis the keystone claims to test. It does not "secretly hand the prompt arm the whole advantage" any more than the adapter is handed it: whatever the adapter receives, a2_tail receives too. The comparison is symmetric on channel. **But it is not a fair test of retrieval.** If the ~124-token conditioning is oracle-injected at inference (the eval hands it to the hypernetwork), then both arms are oracle-conditioned and neither demonstrates a deployable retrieval capability — the keystone becomes a channel-only claim. If it is trajectory-derived, then a2_tail must place the *same trajectory-derived string* (or its downstream product), not the raw gold symbol+definition, or the arms are no longer symmetric on information content. The plan needs one clarifying sentence in Setup naming which regime obtains, and — if oracle-injected — the fallback reframe ("adapter internalizes retrieval") is unsupported by this experiment and must be dropped or run separately. In the informative direction: if a2_tail *loses* to episodic with matched oracle-injected content, the paper has a real claim about weight-vs-prompt delivery holding fixed the information. If a2_tail wins or ties, the keystone reduces to "in the oracle-conditioning regime, delivery channel doesn't matter" — a smaller and honest finding.

**Q2 — Is Option B defensible this round, or disqualifying?**
Defensible *only if paired with substantive engagement of ReasonCACHE's theoretical claim* (see critique 2). On its own — dropping the "we test that boundary directly" clause and naming ReasonCACHE as an unrun comparator — it is a dodge, and a KV/prefix-literate reviewer will read it as one. The problem is not that the arm wasn't run (unrun comparators are acceptable when honestly labelled); it is that ReasonCACHE isn't a neutral comparator. Its abstract asserts a theorem that Rune's mechanism is strictly less expressive. Citing that paper as support *and* declining to test against it *and* not rebutting the theorem is three-in-a-row on the same paper. Fix all three or run Option A. If the target is TMLR (no page limit, methods-forward review culture), Option B + a one-paragraph theoretical engagement will likely clear. If the target is NeurIPS, Option A is the safer bet given how central the KV/token/weight positioning is to the paper's story.

**Q3 — If no disjoint fresh pool with trajectories exists, is prose downgrade sufficient?**
Yes — provided the downgrade is done cleanly and applied consistently. The +0.105 with binom(17,24)=0.064 and a selection-biased CI is a real, reportable observation *as a suggestive finding on a selected configuration*, not as a settled result. Dropping it entirely would be over-correction: it is the metric the objective-grid was tuned against, and reporting it with proper caveats is honest science. The correct downgrade is what the plan already proposes for M1-objective — soften the abstract, acknowledge selection bias, report the p=0.064 across-task sign test as-is, and remove any language ("produces generalising held-out recall") that implies the effect is established. Do *not* invent a fresh pool by generating new trajectories with a modified pipeline just to hit p<0.05 — that would be worse than the current selection bias. The corpus dependency (do disjoint gold trajectories exist?) is a Phase-0 lookup, not a decision point that should hold up the paper.

**Q4 — Encoder ablation: acceptable scope cut or punishable gap?**
Acceptable scope cut, and the right call given the effort budget. "Perceiver beats mean-pool" is what one alternative supports; that is the claim the paper is entitled to make. The stronger "architecture is not what gates this" claim needs the LSTM/transformer runs, and until those runs exist, retiring the stronger claim is the honest move. **Two conditions** for the cut to actually work: (a) the narrowing must be paper-wide, not §3.2-only (see critique 7), and (b) the §6.3 limitations must explicitly name "encoder architecture beyond mean-pool" as untested, in the same list as the direct-PEFT and KV-arm gaps. If a reviewer asks "why not run LSTM?", the answer is "it's on the unrun-comparator list for the next revision" — the same mechanism that handles ReasonCACHE. Not a punishable gap; a properly scoped limitation.

## Missing from plan

- **Explicit disclosure of what the hypernetwork receives at inference time on the keystone.** Load-bearing for Q1 and for the reframe fallback. If it is oracle-injected, the paper's framing needs a broader reconciliation than the plan currently proposes; if trajectory-derived, a2_tail's placed string must be re-specified.
- **A substantive rebuttal (or concession) of ReasonCACHE's rank-expressivity theorem** (see critique 2). Prose-only, but load-bearing under Option B.
- **A corpus check for disjoint tasks with gold trajectories** — the actual gating question for Phase 2a. Should be a Phase 0 lookup, not deferred.
- **Paper-wide narrowing pass for the encoder claim** (Q4 / M5.3). Not just §3.2.
- **A named unrun-comparator commitment mechanism** for ReasonCACHE (and LSTM/transformer encoder) — otherwise "next round" is uncommitted.
- **Recovery-vs-budget-W curve** (P9b) — either accept and add, or decline with a reason.
- **Fig. 2 print-size legibility check** (P9 second half).
- **Family-wise error / multiple-comparison stance** across the four pre-registered gates.
- **Explicit budget accounting for a2_tail** (what 124 tokens of near-cursor code are displaced; whether the isolation control is a "neutral filler" arm).
- **Quantitative gate for the swap control** (critique 5).
- **A realistic NeurIPS-branch effort estimate** if that branch remains live (critique 3).
- **Nothing in the plan addresses whether existing numbers are single-seed / single-training-run** — the review didn't flag this either, so it's out of scope, but worth naming as a category the plan does not touch.
